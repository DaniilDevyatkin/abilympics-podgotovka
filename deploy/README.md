# Публикация сайта через обратный SSH-туннель на VDS

Документ описывает, как сайт «Абилимпикс Башкортостан», который сейчас живёт
только на этой машине, становится доступен из интернета по адресу VDS.
Читать целиком перед первым запуском: здесь же собраны ошибки, из-за которых
туннель «вроде поднят, но снаружи не открывается».

## 1. Зачем именно туннель

Машина стоит за NAT (192.168.51.81/23, шлюз 192.168.50.1), ufw включён с
политикой «входящие запрещены», а провайдер закрывает нестандартные порты —
поэтому входящее соединение из интернета до неё не доходит, и «пробросить
порт» негде: роутер не наш. Исходящие соединения при этом работают свободно,
и это используется: машина сама открывает SSH-соединение к VDS и просит его
слушать порт на своей стороне. Для VDS это обычный входящий SSH-клиент, для
провайдера — обычный исходящий трафик на 22 порт. Ничего не блокируется.

Схема целиком:

    браузер
      |  https://abilimpics.example.ru:443
      v
    VDS: nginx или Caddy  --(127.0.0.1:18099)-->  sshd на VDS
                                                     ^
                                                     | обратный туннель
                                                     | (исходящее SSH с этой машины)
                                                     |
    эта машина: ssh -R 127.0.0.1:18099:127.0.0.1:8099
                serve.py на 127.0.0.1:8099 (статика проекта)

Ключевая деталь — `127.0.0.1` в начале `-R`. Порт 18099 открывается только на
loopback VDS, в интернет он не смотрит: снаружи виден только nginx на 80/443.
Это безопаснее и не требует `GatewayPorts yes` в sshd_config.

## 2. Что должно быть готово на этой машине

Уже сделано:

* `scripts/serve.py` — статический сервер: многопоточный, поддерживает Range
  (иначе встроенный просмотрщик PDF в браузере не листает документ), сжимает
  HTML/CSS/JS/SVG/JSON gzip'ом, отдаёт 304 по ETag и If-Modified-Since.
* `abilympics-web.service` (systemd --user) — держит serve.py на 0.0.0.0:8099
  и перезапускает при падении. Включён в автозапуск.
* `abilympics-tunnel.service` — юнит туннеля. Создан, но **не включён**:
  без параметров VDS он бесполезен, а автозапуск с пустыми переменными
  засорял бы журнал. Включается одной командой, когда появится VDS.
* `~/.ssh/id_ed25519_vds` — отдельная пара ключей только для этого туннеля.
  Приватный ключ лежит на этой машине, публичный нужно один раз добавить
  на VDS.

## 3. Что нужно от владельца VDS

1. IP-адрес и имя пользователя на VDS.
2. Публичный ключ с этой машины в `~/.ssh/authorized_keys` пользователя на VDS:

       ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAILX30bIopgZtB0h7/iHf6v/6k9lXMqaqIj0s0spd1UC7 abilympics-vds

   Добавлять так (на VDS, от нужного пользователя):

       mkdir -p ~/.ssh && chmod 700 ~/.ssh
       echo 'ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAILX30bIopgZtB0h7/iHf6v/6k9lXMqaqIj0s0spd1UC7 abilympics-vds' >> ~/.ssh/authorized_keys
       chmod 600 ~/.ssh/authorized_keys

3. Разрешённый `AllowTcpForwarding` в sshd_config (по умолчанию `yes`).
   `GatewayPorts` менять **не нужно** — мы слушаем loopback.
4. Открытые 80 и 443 в firewall VDS (80 нужен для ACME-проверки Let's Encrypt).
5. Домен или поддомен, направленный A-записью на IP VDS. Без домена сайт
   откроется по `https://IP`, но сертификат будет самоподписанный, и браузер
   покажет предупреждение.

## 4. Порядок действий

### Шаг 1. Проверить, что сервер на этой машине жив

    systemctl --user status abilympics-web --no-pager
    curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8099/

Ожидается `active (running)` и `200`.

### Шаг 2. Заполнить параметры туннеля

    cp deploy/tunnel.env.example ~/.config/abilympics-tunnel.env
    chmod 600 ~/.config/abilympics-tunnel.env
    $EDITOR ~/.config/abilympics-tunnel.env   # REMOTE_HOST, REMOTE_USER, REMOTE_PORT

`REMOTE_PORT=18099` менять не обязательно, главное — чтобы он совпадал с
портом в конфиге nginx/Caddy на VDS.

### Шаг 3. Проверить SSH вручную, до всякого systemd

    ssh -i ~/.ssh/id_ed25519_vds -o BatchMode=yes deploy@IP_VDS 'echo ok; ss -tln | grep 18099'

Должно вывести `ok` и пусто (порт ещё не слушается). Если просит пароль —
ключ не добавлен или неверный пользователь; если `Permission denied` —
проверить права `~/.ssh` (700) и `authorized_keys` (600) на VDS.

### Шаг 4. Поднять туннель и убедиться, что порт появился на VDS

    systemctl --user enable --now abilympics-tunnel
    ssh -i ~/.ssh/id_ed25519_vds deploy@IP_VDS 'ss -tln | grep 18099'

Должна быть строка `127.0.0.1:18099`. Если её нет — смотреть журнал:

    journalctl --user -u abilympics-tunnel -n 30 --no-pager

Типичное: `remote port forwarding failed for listen port 18099` — порт уже
занят на VDS другим процессом, взять другой номер.

### Шаг 5. Настроить веб-сервер на VDS

Caddy (проще, сертификат сам):

    apt install -y caddy
    cat >/etc/caddy/Caddyfile <<'EOF'
    abilimpics.example.ru {
        encode zstd gzip
        reverse_proxy 127.0.0.1:18099
    }
    EOF
    systemctl reload caddy

nginx — готовый конфиг лежит рядом, `deploy/nginx-abilimpics.conf`; заменить
домен, положить в `/etc/nginx/sites-available/`, сделать симлинк в
`sites-enabled/`, затем:

    certbot --nginx -d abilimpics.example.ru
    nginx -t && systemctl reload nginx

### Шаг 6. Проверка снаружи

С этой машины, но по публичному адресу (чтобы проверить именно внешний путь):

    curl -sSI https://abilimpics.example.ru/ | head -3
    curl -sS -o /dev/null -w '%{http_code} %{size_download}\n' https://abilimpics.example.ru/kompetentsii-2026.html
    curl -sS -r 0-1023 -o /dev/null -w '%{http_code}\n' https://abilimpics.example.ru/assets/docs/prigotovlenie-goryachih-zakusok-fv/kz.pdf

Ожидается `200`, `200` и `206` — последний код подтверждает, что Range
доходит до serve.py через туннель и прокси, то есть PDF в браузере листается.

## 5. Ошибки, которые встречаются чаще всего

* **`GatewayPorts` не нужен.** Если поставить `yes`, порт 18099 начнёт
  слушать 0.0.0.0 на VDS и станет доступен из интернета в обход nginx —
  это лишняя дыра. Мы этого не делаем намеренно.
* **Туннель «умирает» через 10 минут простоя.** Лечится `ServerAliveInterval`
  и `ServerAliveCountMax` — они уже в юните. Без них соединение рвётся молча,
  и сайт перестаёт открываться при живом systemd-юните.
* **Двойное сжатие.** Если в nginx включён `gzip on`, а serve.py уже отдал
  `Content-Encoding: gzip`, файл приходит сжатым дважды и браузер показывает
  мусор. В конфиге nginx стоит `gzip off` — не включать.
* **Ошибка в `-R`.** Формат: `-R [bind:]port:host:hostport`. Перепутать
  порядок легко: `-R 127.0.0.1:8099:127.0.0.1:18099` откроет на VDS 8099 и
  будет ходить в 18099 — nginx тогда смотрит в пустоту.
* **Домашний канал — узкое место.** 807 МБ PDF отдаются не со скоростью VDS,
  а со скоростью исходящего канала этой машины. Первый посетитель большого
  PDF будет ждать; при регулярном трафике стоит один раз залить статику
  на VDS через rsync и переключить nginx на файлы вместо туннеля.
* **Машина уснула — сайт лёг.** Это плата за вариант «сайт живёт здесь».
  Если нужна круглосуточная доступность без зависимости от домашней машины,
  статику переносят на VDS.

## 6. Откат

    systemctl --user disable --now abilympics-tunnel
    # на VDS: убрать конфиг nginx/Caddy и перезагрузить веб-сервер
    # при необходимости: удалить строку с ключом abilympics-vds из authorized_keys на VDS

Сайт при этом продолжает работать локально на :8099 — откат публикации
не затрагивает сам контент.
